30-second overview

A connected workflow for a beginner's next decision.

The team explored how exercise discovery, planning, logging, scheduling, and progress review could work as one understandable browser experience.

Problem

Beginners face disconnected choices about exercises, routines, recording, rest, and progress.

Context

Six people built the academic prototype through Scrum-oriented team roles.

My role

Frontend/routing foundations, workflow prototypes, reporting views, and selected maintenance.

Problem and user workflow

Reduce the distance between intention and recorded progress.

A beginner may know the goal—build a consistent routine—without knowing what to choose next or how today's activity relates to prior work.

  1. Discover: browse exercises by muscle group or equipment.
  2. Plan: choose training days, equipment, and a starting point.
  3. Record: enter exercises, sets, repetitions, weight, dates, and notes.
  4. Review: inspect summaries, configurable charts, and sparse-data states.
  5. Adjust: use transparent reminders and scheduling context for the next decision.

The workflow describes a documented academic prototype, not medical guidance or evidence of real-world adoption.

System and data flow

A direct stack with visible boundaries.

The academic monolith made the request path approachable while coupling startup, routing, SQL, business rules, and provider integration more tightly than a production system would.

Route boundary

Client navigation behavior supports usability; API authorization protects data access.

Relational model

User-scoped workouts, entries, exercises, and schedules fit relational queries and ownership rules.

Browser reporting

Client-side summaries kept chart calculations close to the display layer, with long-history performance tradeoffs.

Provider integration

Calendar behavior stayed optional, configuration-dependent, and outside the validated live scope.

Dashboard and reporting thinking

Turn workout history into explainable report states.

This was browser-based reporting design, not an enterprise BI deployment.

  • Defined totals, active periods, exercise summaries, and chart-ready series.
  • Designed line and bar modes, presets, and saved display configuration.
  • Paired charts with readable labels, insight cards, and empty/sparse states.
  • Documented how history data moves from protected endpoints into presentation logic.
  • Kept production scale, executive adoption, and measurable business impact out of scope.

Troubleshooting lessons

Trace the path, make failure actionable, and name the evidence.

01

Follow the system

Page state, routing, API contracts, relational data, and environment configuration often explain one another.

02

Design the failure state

Loading, empty, invalid, offline, unauthorized, and unconfigured states help users and support work.

03

Bound confidence

Static, smoke, database, provider, accessibility, and deployment checks answer different questions.

04

Document the handoff

Consistent structures and explicit ownership boundaries make integration and later maintenance easier.

Limitations and next steps

Useful evidence without a production application claim.

The prototype remains an academic system with incomplete database, provider, accessibility, operational, and scale evidence.

Validation gaps

End-to-end MySQL, live OAuth/Calendar, complete assistive-technology, zoom/reflow, and production application deployment testing remain unestablished.

Architecture limits

The monolithic server and browser-side history processing need clearer module, performance, observability, migration, and recovery boundaries for production use.

Privacy and reliability

Provider lifecycle, small-community privacy edges, long-history behavior, and operational controls require deeper design and testing.

Impact limits

No active-user, adoption, revenue, retention, clinical-effectiveness, enterprise BI, or measurable business-impact result is claimed.

Prioritized next steps

  1. Run representative workflows against a disposable synthetic database.
  2. Expand automated ownership, privacy, and failure-state regression coverage.
  3. Test optional provider behavior with development-only accounts and synthetic events.
  4. Measure long-history reporting performance and conduct broader accessibility review.
