CIS 440 · six-person academic team

Turning workout data into a clearer next step.

A public, code-free case study of the frontend, routing, planning, and visualization work I contributed to a beginner-friendly workout tracker—and how those foundations fit within a team-owned system.

Problem and users

Reduce the distance between intention and action.

Beginners face several connected decisions: what to train, which exercises fit available equipment, how to log a session, when to recover, and how to interpret progress.

The team prototype combined planning, logging, scheduling, progress review, privacy controls, and optional calendar integration in one browser workflow. It is an academic prototype—not medical guidance, production software, or evidence of real-world adoption.

Work
Training-day/equipment/start-date controls, a multi-week preview, entry integration, reminder heuristics, and duplicate-notice suppression.

Deterministic interface guidance, not personalized medical advice.

Architecture and data flow

A straightforward stack with visible boundaries.

A compact monolith helped the team trace the full request path, while also concentrating startup, routing, SQL, authentication, and provider concerns.

Authentication

Bearer tokens protect API requests; a client navigation guard is usability support, not server authorization.

Relational data

Parameterized queries connect users, exercises, workouts, entries, and schedules with ownership boundaries.

Browser analytics

Client-side summaries made chart experimentation accessible, with performance tradeoffs for long histories.

PWA and calendar

The service worker provides a static shell; Calendar remains optional and needs stronger token lifecycle controls.

Responsible public release

Publish the explanation without publishing private history.

  • Code-free: no application source, SQL, environment file, dependency tree, or private Git history.
  • Synthetic: interface values and diagrams do not represent a real account or workout record.
  • Role-only: six-person context is preserved while other contributor names are omitted pending their individual publication preferences.
  • Asset-safe: private screenshots and unclear original media are excluded; the social card and diagrams were created for this release.
  • Credential-safe: no credential value is copied or tested; historical material requires owner-controlled remediation.
  • Separate source gate: the sanitized source candidate remains local, Git-free, and unpublished throughout Stage 1 pending direct team review and a separate Phase 2 authorization.

Limitations and next steps

The prototype is useful because its boundaries are visible.

Security and sessions

The reconstructed source adds tab-scoped bearer storage, server-checked session versions, step-up checks, bounded throttles, encrypted provider grants, and browser-bound OAuth state. Secure-cookie sessions, shared multi-instance controls, mailbox verification, and tested key rotation remain future work.

Validation

Local dependency, static, smoke, and responsive-layout evidence is bounded; database, live OAuth, assistive-technology, and deployment evidence remains incomplete.

Reliability and scale

The monolithic server, runtime schema compatibility work, unbounded history patterns, and best-effort external synchronization need production-oriented engineering.

Privacy and accessibility

Community edge cases, browser-local account state, data lifecycle, keyboard flows, reflow, contrast, and assistive-technology behavior need broader testing.

Prioritized next steps

  1. Maintain the authorized code-free case study and repeat public-snapshot checks after future changes; keep source publication disabled until direct team review and a separate Phase 2 authorization.
  2. Add authorization, privacy, date, and account-lifecycle regression tests.
  3. Exercise a disposable synthetic database and explicitly record skipped integrations.
  4. Replace process-local rate/OAuth state with shared controls; add mailbox verification, key rotation, observability, and migration rollback.
  5. Complete keyboard, screen-reader, zoom/reflow, contrast, and reduced-motion review.

Transferable lessons

Trace the whole system, make failure actionable, and bound confidence.

01

Follow the path

Browser state, API contracts, SQL relationships, and environment configuration often explain one another.

02

Design failure states

Loading, empty, invalid, offline, and unauthorized states help users and operators understand what happened.

03

Name the evidence

A static review, smoke test, database test, and deployment test answer different questions.

04

Design for handoffs

Consistent structure and explicit boundaries make integration, support, and release work easier.
